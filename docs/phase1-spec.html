Design spec · Phase 1 · working name

Lockstep Phase One

An additive sync from a Git repository into Fusion's Data Panel. Downloads only what changed, never touches a file it already placed, and refuses to guess. Phase 2 — in-place updates — is deliberately out of scope.

Target Fusion add-in, any repo Reference corpus VEX-CAD, 1,193 files Status Draft for review
Invariant — everything else follows from this

Never call uploadFile on a path already recorded in the manifest. Fusion accepts same-named files in one folder without warning, error, or rename. A duplicate upload is silent corruption the user cannot see and cannot undo.

Phase 1 modifies nothing that already exists. Its worst failure mode is a redundant file, never a broken one — and the invariant above is what keeps even that off the table.

01

Shape

An add-in, not a script and not a CLI. The operations it needs — uploadFile, documents.open, Document.save — exist only inside Fusion's Python runtime. An add-in persists across restarts and can own a toolbar button; a script cannot.

Distribution is GitHub plus GitHubToFusion360 on day one. The Autodesk App Store needs a .bundle, a publisher agreement and a review cycle — worth doing once the tool is stable and the audience is wider than one Discord.

Name is provisional. “Lockstep” is a placeholder chosen so the spec reads cleanly. Whatever it ends up as, keep VEX out of it — the tool is general and the reference corpus is not the product.
02

Configuration

One config, many sources. A user syncing three libraries is the normal case, not an edge case.

{
  "schema": 1,
  "sources": [
    {
      "id": "vex-cad",                    // stable key, names the manifest file
      "label": "VEX CAD Library",
      "repo": "VEX-CAD/VEX-CAD-Fusion-360-Library",
      "ref": "main",                       // branch or tag
      "subpath": "",                       // sync only below this
      "include": ["**/*.f3d", "**/*.step"],
      "exclude": ["**/_archive/**"],
      "target": {
        "project_id": "urn:adsk...",       // resolved once, then stored
        "folder_path": "Libraries/VEX"      // created if absent
      }
    }
  ]
}

Store project_id, never the project name — names are editable and duplicable. Resolve the folder path to a DataFolder id on first sync and cache that too.

03

Manifest

One manifest per source. This is the entire state of the system, and its job is to answer one question for every path: have I already placed this, and which cloud file is it?

{
  "schema": 1,
  "source_id": "vex-cad",
  "repo": "VEX-CAD/VEX-CAD-Fusion-360-Library",
  "ref": "main",
  "synced_commit": "f13995dd65f5...",   // tree we last reconciled against
  "synced_at": "2026-09-06T20:50:00Z",
  "files": {
    "Motion/LS Shaft.f3d": {
      "blob":    "a3f9c1...",             // git blob SHA - change detection
      "lineage": "urn:adsk.wipprod:dm.lineage:n-W4fL...",
      "version": 1,
      "state":   "placed",               // placed | inflight | adopted
      "at":      "2026-09-06T20:44:11Z"
    }
  }
}

Why lineage, never name

Testing confirmed Fusion will hold three files called SyncProbe in one folder, each on its own lineage URN, with no suffix and no complaint. Name lookup would silently pick the wrong one. The lineage URN is the only stable identity, and it is what Phase 2 will need to open a file for update.

Where it lives

A JSON file beside the add-in, one per source. This is per-machine, so a user on a laptop and a desktop has two views of one cloud library — accepted for v1, mitigated by rebuild-from-folder (§05) being a first-class command rather than a recovery hack.

04

The sync algorithm

plan(source):
    tree     = GET /repos/{repo}/git/trees/{ref}?recursive=1   # 1 request
    remote   = { path: blob_sha  for path in tree if matches include/exclude }
    manifest = load(source.id)

    add    = { p for p in remote if p not in manifest }
    change = { p for p in remote if p in manifest
                                 and remote[p] != manifest[p].blob }
    orphan = { p for p in manifest if p not in remote }
    return add, change, orphan

apply(plan):                       # only after the user confirms a dry run
    for p in add:                    # the only writing path in Phase 1
        mark_inflight(p)
        blob = download(p)
        df   = folder_for(p).uploadFile(blob)
        wait(df)                      # DataFileFuture -> Finished
        record(p, blob_sha, df.id, "placed")
        flush_manifest()              # after every file, not at the end

    for p in change: report_only(p)   # Phase 2
    for p in orphan: report_only(p)   # cannot delete

Three sets, one write path. Everything risky is a report until Phase 2 earns the right to act on it.

Flush after every file, not at the end. A crash mid-sync must leave a manifest that accurately describes what is in the cloud — otherwise the next run re-uploads and violates the invariant.

05

Adopt mode — the one that decides adoption

Every existing user of the VEX library has 1,193 files already imported and no manifest. Point a naive sync at their folder and it sees 1,193 unknown paths, uploads all of them, and doubles their entire library in silence. This is not an edge case; it is the majority of the userbase on day one.

Adopt against a release, not against HEAD

The obvious implementation — match local files to the current tree and record today's blob SHAs — is wrong. A user whose library came from v2.0.3 would have their stale files recorded as current, and those files would never update again.

Instead, ask which release they installed and adopt against that tag's tree. Their manifest then honestly describes what they have, and the very next sync computes a correct delta from v2.0.3 to HEAD.

adopt(source, from_ref):
    tree  = tree_at(from_ref)                 # e.g. tag v2.0.3
    local = scan(target_folder)               # {relative path: DataFile}

    matched   = paths in both
    only_here = paths in local, not in tree   # user's own files - leave alone
    missing   = paths in tree, not in local   # becomes 'add' on first sync

    # dry run reports all three counts and stops
    on confirm:
        for p in matched:
            record(p, tree[p].blob, local[p].id, state="adopted")

Adoption writes manifest entries and uploads nothing. If the user cannot say which release they have, offer “unknown”: record the lineage with blob: null, which marks every file as needing verification and defers it to Phase 2 rather than guessing.

The same scan powers rebuild-from-folder, the recovery path for a lost or stale manifest.

06

Path mapping

Repo paths are not Data Panel paths, and the reference corpus is a good adversary. Measured against VEX-CAD at v2.0.5:

PropertyValueConsequence
Deepest nesting7 levelsFolder creation must be recursive and cached
Longest path135 charsCheck Fusion's limit before assuming it fits
Non-ASCII names5 files0.5” OD HS Spacer… uses U+201D, not a straight quote
Leading punctuation1 file! Unpin metal, move in… — sorts oddly, may confuse pickers
Characters in use! & ( ) + , - ”Commas and parens are normal here, not exceptional
Measured with git ls-files across 1,193 tracked files.

Rules

  1. Preserve names verbatim wherever Fusion accepts them. Renaming breaks the user's mental map of the library.
  2. Never normalise Unicode. Folding U+201D to " would make the manifest path and the repo path disagree, and every subsequent sync would see a phantom change.
  3. Strip the extension for the Data Panel name — Fusion supplies its own — but key the manifest on the repo path including extension.
  4. If a name must be altered to be accepted, record both the repo path and the placed name in the manifest, and surface it in the report. A silent rename is a future duplicate.
07

Failure and resume

Uploads are asynchronous and slow — measured at 18.3s and 7.2s for a single 155 KB file. A first sync is thousands of them. It will be interrupted.

The dangerous window is between a successful upload and the manifest write recording it. Crash there and the next run re-uploads a file that already exists, which is exactly the invariant violation.

# two-phase record closes the window
mark_inflight(path)      # written BEFORE the upload starts
upload → wait → ok
record(path, ..., "placed")

# on next launch
for p in manifest where state == "inflight":
    # truth is in the cloud, not the manifest - go look
    hits = scan_folder_for(p)
    if len(hits) == 1: record(p, ..., "placed")     # it landed
    elif len(hits) == 0: drop(p)                    # retry safely
    else: flag_for_human(p)                       # already duplicated

A file that fails mid-run is logged and skipped; the run continues and reports failures at the end. One bad file must never abort a 1,193-file sync.

08

Network

Two download strategies, chosen by size — because the bootstrap case and the update case are not the same problem.

  • Bootstrap (hundreds of files): fetch codeload.github.com/{repo}/tar.gz/{ref} once and unpack. One connection instead of 1,193.
  • Delta (tens of files): fetch each from raw.githubusercontent.com. Not counted against the API rate limit.
  • Threshold: start at 100 files, tune with real timings.

The tree request is the only call against the API proper — one per sync, against an unauthenticated limit of 60/hour. Ample, and a headroom check should still fail loudly rather than mysteriously.

09

User flow

Every path through the tool ends in a preview the user must confirm. There is no fire-and-forget mode in Phase 1.

Utilities → Lockstep → Sync Library

  first run   → no manifest found
                → "Do you already have this library imported?"
                   yes → ADOPT: pick release → dry run → confirm
                   no  → FRESH: pick project + folder → dry run → confirm

  later runs  → fetch tree, diff, dry run:

                   + 25 files to add          117 MB    ~4 min
                   ~  2 files changed         skipped   (Phase 2)
                   -  0 files gone upstream    reported

                → [Cancel]  [Sync]

Progress shows current file, count and elapsed time, and stays cancellable — a cancel mid-run is safe by construction, because the manifest is flushed per file.

10

Acceptance criteria

  • A1 · idempotenceRunning sync twice with no upstream change uploads zero files and leaves the folder count unchanged.
  • A2 · adoptionAdopting an existing 1,193-file library uploads nothing and produces a manifest with 1,193 entries.
  • A3 · deltaAdopting at v2.0.3, then syncing to v2.0.5, adds exactly the files those releases added — and nothing else.
  • A4 · crash safetyKilling Fusion mid-sync and relaunching produces no duplicates; inflight entries reconcile against the cloud.
  • A5 · hostile pathsAll five U+201D filenames and the leading-! file round-trip: placed, recorded, and seen as unchanged on the next run.
  • A6 · no silent renameAny name altered to satisfy Fusion appears in the run report.
  • A7 · failure isolationOne unreachable file does not abort the run and is listed at the end.
  • A8 · read-only honestyA dry run writes nothing — verified by comparing folder contents and manifest before and after.

A3 and A5 are the ones that will actually fail first. Build fixtures for them before building the UI.

11

Open questions

  • Fusion's path and name limits. The 135-character path is untested. Find the ceiling before a user does.
  • Does uploadFile preserve the filename exactly for the U+201D cases, or does it normalise? Determines whether rule 2 in §06 is sufficient.
  • Bootstrap throughput. At ~8–18s per upload, 1,193 files is hours, not the ~7 minutes fusion-batch-import reports. Understand that gap before promising a number.
  • Multi-machine manifests. Accepted as broken in v1. Fusion document attributes could make the cloud data self-describing, at the cost of an open per file.

Import approach follows zeulewan/fusion-batch-import, which proved Data Panel bulk import with folder structure preserved.
